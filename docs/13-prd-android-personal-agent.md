我建议将产品定义为：

Android Personal Agent：一个运行在 Android 手机上的本地优先、系统级、可持续运行的个人智能体操作系统入口。

它不是把 ChatGPT 搬到手机上，也不是简单集成几个 AI 工具，而是让 Agent 真正拥有手机上的执行能力、个人上下文、长期记忆和自主任务编排能力。

产品能力借鉴三类业界产品的设计思路：

- Dot：个人化、长期记忆、主动感知、持续陪伴。
- Cue：上下文理解、任务组织、信息关联、主动辅助。
- Muse：Agent 自动化、工具执行、隔离运行环境、多步骤任务。

在此基础上，增加一个核心差异化：模型在本地运行，数据默认不出设备，工具执行由 Android 系统级安全机制管理。

以下文档将覆盖产品能力、功能边界、页面交互、用户体验、系统权限、离线模型、后台运行、安全机制和验收标准，并将产品设计与技术实现约束对应起来。

# Android Personal Agent 产品需求文档（PRD）

**产品名称：** Android Personal Agent\
**产品定位：** 本地优先的系统级个人智能体\
**文档版本：** V1.0\
**产品形态：** Android 原生应用 + 系统级 Agent Runtime\
**目标用户：** Android 手机用户、AI 重度用户、效率工具用户、开发者及隐私敏感用户

---

# 一、产品概述

## 1.1 产品背景

当前移动端 AI 产品主要存在四类问题：

1. **只会对话，不会真正执行。** 大多数 AI 助手停留在问答、文本生成层面，无法持续操作手机中的应用、文件和系统能力。
2. **缺乏长期个人记忆。** 每次对话都需要重新提供上下文，无法形成稳定的个人知识和行为习惯。
3. **能力分散。** 浏览器、文件管理、代码执行、日程管理、自动化等能力分布在不同应用中，缺少统一 Agent 调度入口。
4. **云端依赖严重。** 模型推理、数据处理和任务执行通常依赖网络，个人数据需要上传云端，存在隐私和可用性问题。

因此，构建一个真正运行在 Android 手机上的 Personal Agent，使其从聊天工具升级为具备个人上下文、工具调用、任务规划和持续执行能力的智能体。

## 1.2 产品愿景

打造一个能够理解用户、了解设备、掌握个人信息、调用手机能力，并持续帮助用户完成任务的本地 AI 助手。

产品核心理念：

- Local First：本地模型优先，默认离线可用。
- Personal Memory：建立长期个人记忆。
- Agentic Execution：不只回答问题，还能执行任务。
- System Integration：深入 Android 系统能力。
- Privacy by Design：权限可控、数据可控、执行可审计。
- Always Available：支持持续运行、后台任务和主动提醒。

## 1.3 产品核心价值

| 维度  | 传统 AI 助手 | Personal Agent |
| --- | -------- | -------------- |
| 交互  | 一问一答     | 对话、任务、主动服务     |
| 模型  | 云端为主     | 本地模型优先         |
| 记忆  | 会话上下文    | 长期个人记忆         |
| 工具  | 有限插件     | Android 系统工具体系 |
| 执行  | 返回操作建议   | 真实调用工具执行       |
| 自动化 | 单次操作     | 多步骤任务和定时任务     |
| 数据  | 云端处理为主   | 本地存储和处理        |
| 运行  | 前台交互     | 前台、后台、任务恢复     |

## 1.4 产品设计原则

**原则一：一个入口，多个 Agent。**

用户只需要面对一个 Personal Agent，内部可以根据任务类型路由到不同领域 Agent。

例如：

- 主 Agent：任务理解、规划、决策、调度。
- 日程 Agent：日程查询、创建、修改。
- 文件 Agent：文件检索、分类、摘要。
- 浏览器 Agent：网页访问、内容提取。
- 系统 Agent：设备信息、应用控制、系统 API。
- 开发 Agent：Shell、Python、代码分析和执行。

**原则二：本地优先，不代表所有能力都必须依赖大模型。**

简单操作通过原生 API 和规则执行；复杂任务通过本地模型推理；高风险操作需要用户确认。

**原则三：Agent 有执行能力，但没有无限权限。**

Agent 只能调用已注册、已授权、受策略约束的工具。

**原则四：任务必须可见、可控、可恢复。**

用户随时知道 Agent 正在做什么，可以暂停、取消、查看过程和撤销支持撤销的操作。

# 四、核心模块详细需求

# 4.1 首页：Personal Agent 智能入口

## 4.1.1 产品目标

提供统一的自然语言交互入口，使用户能够通过一句话发起任意任务。

首页不能只是聊天记录列表，而应该是一个个人智能体的工作空间。

## 4.1.2 页面布局

首页建议分为五个区域：

**A. 顶部状态栏**

显示：

- Personal Agent 品牌标识。
- 当前模型，例如 Qwen 3B。
- Local / Offline 状态。
- Agent 在线运行状态。

点击模型名称进入模型详情；点击运行状态查看后台运行情况。

**B. Agent 欢迎区域**

根据用户历史活动展示个性化问候。

示例：

“早上好，今天有三个待处理事项。”

“昨天下载的文档还没有整理，需要我帮你归档吗？”

注意：主动建议必须有明确数据来源和授权，不允许虚构用户行为。

**C. 主动任务卡片**

展示 Agent 可以帮助用户完成的事项：

- 整理最近下载文件。
- 汇总本地文档。
- 检查今天的日程。
- 继续上次未完成任务。
- 根据最近授权的上下文提供建议。

**D. 对话区域**

支持：

- 文字输入。
- 语音输入。
- 图片输入。
- 文件输入。
- 任务引用。
- 记忆引用。

**E. 底部快捷能力**

- 文件处理。
- 图片理解。
- 代码执行。
- 任务自动化。
- 设备控制。

## 4.1.3 对话交互设计

对话采用类似 ChatGPT 的气泡布局，但要增加 Agent 执行状态。

用户：

“帮我整理最近下载的 PDF，按主题分类，并生成一个汇总。”

Agent：

“我准备执行以下操作：

1. 扫描下载目录中的 PDF。
2. 提取文档标题和正文。
3. 根据内容进行主题分类。
4. 创建分类目录。
5. 生成汇总文档。

预计处理 12 个文件。”

底部提供：

- 开始执行。
- 查看任务计划。
- 修改计划。

执行过程中，Agent 需要展示实时进度：

```
正在执行任务

✓ 扫描下载目录
✓ 识别 12 个 PDF
✓ 提取文档内容
● 正在分析文档主题
○ 创建分类目录
○ 生成汇总文档

当前进度：3 / 6
```

执行完成后：

```
任务完成

处理文件：12 个
创建分类：4 个
生成报告：1 份

[查看报告] [查看文件] [再次执行]
```

## 4.1.4 对话特殊能力

**上下文引用**

用户可以在对话中引用：

- 某次历史任务。
- 某份文件。
- 某条长期记忆。
- 某个 Agent。
- 某个 Skill。

**多轮任务**

例如：

用户：“帮我整理一下项目文档。”

Agent：“需要按照项目分类，还是按照文档类型分类？”

用户：“按照项目。”

Agent：“明白，我会保留原始文件，并在新目录中生成分类副本。”

Agent 必须将多轮对话转化为一个持续任务上下文，避免每轮重新规划。

**任务执行与普通回答区分**

普通问答不应显示虚假的执行动画。

只有真正发起工具调用时，才展示工具执行状态。

# 4.2 Agent 工作台：任务规划与自动执行

## 4.2.1 产品目标

将 Agent 从对话机器人升级为任务执行系统。

借鉴 Muse 的自动化执行理念，以及 Cue 的上下文任务组织方式。

## 4.2.2 任务类型

支持六类任务：

| 任务类型 | 示例                 |
| ---- | ------------------ |
| 信息获取 | 查询本地文件、提取网页内容      |
| 内容生成 | PPT、Markdown、总结、代码 |
| 文件操作 | 搜索、整理、复制、重命名       |
| 系统操作 | 获取设备信息、打开应用        |
| 自动化  | 定时提醒、周期性整理         |
| 复杂任务 | 多步骤、多工具、多 Agent 协同 |

## 4.2.3 任务生命周期

```
用户输入
   ↓
任务理解
   ↓
上下文检索
   ↓
任务规划
   ↓
风险识别
   ↓
权限检查
   ↓
工具调度
   ↓
执行监控
   ↓
结果校验
   ↓
结果交付
   ↓
记忆沉淀
```

每一个任务必须有唯一 Task ID。

任务状态：

- Draft：草稿。
- Planning：规划中。
- Waiting Approval：等待用户授权。
- Ready：等待执行。
- Running：执行中。
- Paused：暂停。
- Completed：完成。
- Failed：失败。
- Cancelled：已取消。
- Interrupted：被系统中断，等待恢复。

## 4.2.4 任务详情页

任务详情页采用时间线结构。

展示：

1. 用户原始需求。
2. Agent 的任务理解。
3. 执行计划。
4. 子任务和 Agent 分工。
5. 工具调用记录。
6. 文件读写记录。
7. 执行进度。
8. 异常与重试。
9. 最终交付结果。

每个步骤支持展开查看详细信息。

例如：

```
任务：整理手机项目资料

主 Agent
  ├── 文件 Agent
  │     ├── 扫描文件
  │     └── 提取元数据
  │
  ├── 内容 Agent
  │     ├── 文档摘要
  │     └── 分类标签
  │
  └── 文件管理 Agent
        ├── 创建目录
        └── 生成分类副本
```

## 4.2.5 任务控制

用户可以：

- 暂停任务。
- 恢复任务。
- 终止任务。
- 修改未执行步骤。
- 重新执行失败步骤。
- 查看执行日志。
- 撤销支持回滚的操作。

注意：任务恢复不能简单地从上一次模型输出继续执行，必须从持久化任务状态恢复，并重新校验权限和执行前置条件。

## 4.2.6 自动化任务

支持创建：

- 一次性定时任务。
- 每日任务。
- 每周任务。
- 条件触发任务。
- 事件触发任务。

示例：

“每天晚上 10 点帮我整理当天下载的文件。”

配置内容：

- 任务名称。
- 执行时间。
- 触发条件。
- 使用 Agent。
- 使用工具。
- 权限范围。
- 是否需要执行确认。
- 失败处理策略。

后台执行受 Android 系统调度、应用待机、Doze 和电量策略约束，不能承诺任意时间都能精确执行。

# 4.3 工具中心：Agent 能力生态

## 4.3.1 产品目标

建立统一的工具注册、发现、授权、调用和管理中心。

工具不应只是普通应用插件，而应该成为 Agent 可调用的标准化能力。

## 4.3.2 工具分类

### 第一类：Android 原生工具

- 设备信息。
- 文件访问。
- 应用启动。
- 通知管理。
- 日历操作。
- 剪贴板。
- 系统设置跳转。
- 媒体信息。
- 联系人操作。
- 位置服务。

涉及敏感权限的能力必须由独立权限策略控制。

### 第二类：内容处理工具

- PDF 解析。
- Office 文档处理。
- 图片 OCR。
- 图片理解。
- 语音转文字。
- 文字转语音。
- 文件格式转换。
- Markdown 处理。

### 第三类：开发执行工具

- Shell。
- Python。
- JavaScript。
- Git。
- 文件读写。
- 代码分析。
- 本地脚本执行。

### 第四类：浏览器工具

- 打开网页。
- 网页内容提取。
- 页面截图。
- 网页搜索（离线环境下不可用）。
- 表单填写。
- 页面操作。

网页自动化需要浏览器自身支持，不能将普通 WebView 当作完整浏览器自动化环境。

### 第五类：Agent Skills

Skill 是具备明确输入、输出、执行约束和依赖关系的可复用能力包。

例如：

- PDF 批量分析 Skill。
- 项目文档整理 Skill。
- Android 性能分析 Skill。
- 代码审查 Skill。
- 会议纪要生成 Skill。

每个 Skill 包含：

```
skill/
├── manifest.json
├── SKILL.md
├── instructions/
├── scripts/
├── resources/
└── permissions.json
```

其中 manifest 描述：

- Skill ID。
- 名称和版本。
- 描述。
- 输入参数。
- 输出结构。
- 依赖工具。
- 所需权限。
- 风险等级。
- 执行环境。
- 网络要求。

## 4.3.3 工具详情页

每个工具需要展示：

- 工具名称。
- 能力描述。
- 适用场景。
- 输入和输出。
- 执行环境。
- 所需权限。
- 网络依赖。
- 资源消耗。
- 最近调用时间。
- 执行成功率。

提供：

- 启用 / 禁用。
- 授权管理。
- 试运行。
- 查看日志。
- 移除工具。

## 4.3.4 工具调用规范

Agent 不允许直接执行任意工具命令。

所有调用必须经过 Tool Broker。

统一调用流程：

```
Agent
  ↓
Tool Registry
  ↓
Policy Engine
  ↓
Permission Check
  ↓
Tool Broker
  ↓
Execution Worker
  ↓
Result Validator
  ↓
Agent
```

所有工具采用统一的结构化输入输出，工具异常需要明确返回错误码，不能将异常伪装成成功结果。

# 4.4 记忆中心：Personal Memory

## 4.4.1 产品目标

让 Agent 能够持续了解用户的偏好、历史任务、常用信息和个人知识。

记忆不是简单的聊天记录，而是经过提取、分类、管理和检索的长期上下文资产。

## 4.4.2 记忆分类

| 类型                | 说明      | 示例            |
| ----------------- | ------- | ------------- |
| Profile Memory    | 稳定个人偏好  | 喜欢简洁的回答       |
| Preference Memory | 行为和使用习惯 | 默认使用 Markdown |
| Episodic Memory   | 事件记忆    | 上周完成某个项目      |
| Task Memory       | 任务记忆    | 上次文件整理的规则     |
| Knowledge Memory  | 知识记忆    | 项目技术方案        |
| Context Memory    | 临时上下文   | 当前正在处理的文档     |

## 4.4.3 记忆管理

记忆必须可见、可编辑、可删除。

用户可以：

- 查看所有记忆。
- 搜索记忆。
- 修改记忆。
- 删除记忆。
- 禁止某些内容进入记忆。
- 设置自动记忆策略。
- 查看记忆来源。

记忆详情必须展示：

- 记忆内容。
- 记忆分类。
- 创建时间。
- 信息来源。
- 使用次数。
- 置信度或可信状态。
- 最近更新时间。

## 4.4.4 记忆写入流程

```
对话 / 任务结果
      ↓
记忆候选提取
      ↓
重要性判断
      ↓
敏感信息过滤
      ↓
去重与合并
      ↓
记忆存储
      ↓
用户查看与管理
```

V1.0 建议采用自动提取 + 用户可审查的机制。

不能因为用户在一次对话中提及某个信息，就默认永久记忆。

## 4.4.5 记忆检索

用户发起任务时：

1. 提取任务关键词。
2. 查询相关长期记忆。
3. 检索关联历史任务。
4. 检索授权知识库。
5. 将相关上下文传给主 Agent。

检索结果需要保留来源，避免将模型推测误认为用户真实信息。

# 4.5 本地模型中心：Local AI Runtime

## 4.5.1 产品目标

提供完全运行于手机端的模型管理和推理能力。

本地模型是整个产品的核心基础设施，而不是一个可有可无的配置选项。

## 4.5.2 模型管理

支持：

- 模型列表。
- 模型下载。
- 本地导入。
- 模型删除。
- 模型切换。
- 模型版本管理。
- 量化版本选择。
- 模型完整性校验。
- 模型运行状态监控。

## 4.5.3 模型分类

| 模型类型         | 用途                    |
| ------------ | --------------------- |
| 通用语言模型       | 对话、规划、推理              |
| 代码模型         | Shell / Python / 代码辅助 |
| Embedding 模型 | 本地知识检索                |
| Vision 模型    | 图片理解                  |
| ASR 模型       | 语音识别                  |
| TTS 模型       | 语音生成                  |

建议将模型分成三个档位：

- 轻量模型：适用于低内存手机。
- 标准模型：适用于主流旗舰设备。
- 高性能模型：适用于高内存、高算力设备。

具体模型的选择由设备内存、NPU/GPU 支持情况、运行时兼容性和实际压测决定。

## 4.5.4 模型详情页

展示：

- 模型名称。
- 参数规模。
- 量化版本。
- 文件大小。
- 所需运行内存估计。
- 上下文窗口。
- 推理后端。
- 下载状态。
- 当前运行状态。

模型运行时展示：

- 当前加载状态。
- 首 Token 延迟。
- 生成速度。
- 内存占用。
- CPU / GPU / NPU 使用情况（以平台实际可获得数据为准）。
- 当前上下文长度。
- 温度及异常状态（如可获取）。

## 4.5.5 本地模型配置

用户可以设置：

- 默认模型。
- 主 Agent 模型。
- 代码 Agent 模型。
- 图片理解模型。
- 最大上下文长度。
- 最大生成长度。
- 温度参数。
- 推理线程。
- 最大内存预算。
- 是否允许后台推理。
- 低电量时是否暂停推理。

## 4.5.6 模型调度策略

不建议所有任务都调用同一个大模型。

采用分级调度：

```
用户任务
   ↓
任务复杂度判断
   ↓
规则 / 原生 API
   ↓
轻量模型
   ↓
主模型
   ↓
领域模型
```

例如：

- 打开应用：原生 API。
- 查询简单设备信息：系统工具。
- 整理文件：轻量模型 + 文件工具。
- 复杂任务规划：主模型。
- 代码分析：代码模型。
- 图片理解：视觉模型。

模型无法加载时，需要提供明确错误和降级方案，不能假装完成推理。

## 4.5.7 离线运行要求

产品首次安装后，在不联网的情况下仍然能够：

- 加载已安装的模型。
- 完成文本对话。
- 调用已安装工具。
- 查询本地记忆。
- 处理授权文件。
- 执行已配置的本地自动化。
- 查看历史任务。

模型下载、Skill 下载、外部网页访问等功能需要网络，必须明确标注网络依赖。

# 4.6 系统与安全中心

## 4.6.1 产品目标

让用户清楚知道 Agent 拥有哪些权限、正在使用什么能力、可以访问哪些数据。

## 4.6.2 权限分类

| 权限类型  | 示例      | 默认策略     |
| ----- | ------- | -------- |
| 文件权限  | 读取文档    | 按目录或文件授权 |
| 文件写入  | 创建、修改文件 | 单独授权     |
| 应用权限  | 启动应用    | 按能力授权    |
| 联系人   | 读取联系人   | 默认关闭     |
| 日历    | 查询、修改日程 | 分别授权     |
| 位置    | 获取设备位置  | 默认关闭     |
| 摄像头   | 图片采集    | 按次授权     |
| 麦克风   | 语音采集    | 按次或会话授权  |
| Shell | 执行命令    | 高风险授权    |
| 网络    | 访问外部网络  | 默认禁止     |
| 无障碍   | UI 自动化  | 独立风险提示   |

注意：Android 权限、系统签名权限、特殊访问权限和厂商特权接口并不等价，产品不能将所有系统能力都包装成普通用户授权。

## 4.6.3 权限管理页面

展示：

- 已授权工具。
- 未授权工具。
- 正在使用权限的任务。
- 最近权限调用。
- 高风险操作记录。
- 一键撤销授权。

每项权限必须包含：

- 权限用途。
- 关联工具。
- 数据访问范围。
- 授权时间。
- 是否允许后台使用。
- 是否需要再次确认。

## 4.6.4 高风险操作确认

以下操作必须设置额外确认策略：

- 删除文件。
- 批量修改文件。
- 发送消息。
- 发送邮件。
- 支付或资金操作。
- 修改系统关键设置。
- 执行高风险 Shell 命令。
- 安装或卸载应用。

确认界面必须明确展示操作对象和影响范围。

例如：

“即将删除 Downloads 目录中的 23 个文件。”

而不是仅仅显示：

“Agent 需要文件权限。”

## 4.6.5 操作审计

所有工具调用需要记录：

- Task ID。
- Agent ID。
- Tool ID。
- 调用时间。
- 调用参数摘要。
- 权限判断结果。
- 执行结果。
- 执行耗时。
- 错误信息。

密码、Token、密钥和敏感原始数据不得写入普通日志。

# 五、关键交互体验设计

## 5.1 体验一：自然语言到任务执行

场景：用户希望整理手机文件。

流程：

1. 用户在首页输入自然语言。
2. Agent 理解用户目标。
3. Agent 检索相关记忆和文件上下文。
4. 生成执行计划。
5. 展示文件操作范围。
6. 用户确认。
7. Agent 调用文件工具。
8. 展示实时进度。
9. 生成结果报告。
10. 将可复用规则作为记忆候选。

体验要求：

- 用户不需要理解工具名称。
- 不需要手动编排 Skill。
- 任务执行过程透明。
- 高风险操作必须有确认。
- 结果必须可验证。

## 5.2 体验二：主动式个人助手

借鉴 Dot 的主动服务体验。

首页不应等待用户输入，可以在用户授权后展示：

- 未完成任务提醒。
- 最近文档处理建议。
- 定时任务执行结果。
- 相关知识关联。
- 用户主动订阅的事件提醒。

主动建议分为三类：

**信息型：** 提醒用户有某个事项。

**建议型：** 根据已有上下文推荐一个操作。

**执行型：** 满足明确授权和触发条件后，自动执行低风险任务。

重要要求：

主动建议不是无限制监听手机活动。必须基于明确授权的数据源、事件订阅和用户配置运行。

## 5.3 体验三：多 Agent 协作

用户输入：

“帮我分析这个项目，生成技术架构文档。”

主 Agent：

- 理解需求。
- 制定计划。
- 分配领域 Agent。

文件 Agent：

- 搜索项目文件。
- 提取文档内容。

代码 Agent：

- 分析代码结构。
- 提取依赖关系。

架构 Agent：

- 组织架构信息。
- 生成技术方案。

文档 Agent：

- 生成 Markdown 文档。

主 Agent：

- 汇总结果。
- 检查完整性。
- 交付用户。

交互要求：

- 显示主 Agent 和子 Agent 分工。
- 显示各 Agent 执行状态。
- 展示任务依赖关系。
- 用户可以查看每个 Agent 的输出。
- 失败后可以只重试失败节点。

V1.0 可以先采用主 Agent + 领域 Agent 的逻辑协作，不要求所有 Agent 都运行独立大模型进程。

## 5.4 体验四：本地离线模式

用户打开飞行模式。

首页展示：

“本地模式已启用，所有当前可用能力均在设备上执行。”

可以继续使用：

- 本地模型。
- 本地记忆。
- 文件处理。
- 本地 Skills。
- 原生 Android 工具。
- 历史任务。
- 离线知识库。

对于网络依赖任务：

“该任务需要访问外部网页，当前处于离线状态。”

提供：

- 保存任务。
- 使用本地资料继续。
- 取消任务。

禁止静默切换云模型或上传文件。

## 5.5 体验五：任务中断恢复

例如，用户执行一项 30 分钟的文件分析任务，中途关闭应用。

再次打开后：

展示：

“上次任务尚未完成。”

用户可以：

- 恢复任务。
- 查看已完成步骤。
- 取消任务。
- 查看中断原因。

恢复前需要重新校验：

- 任务状态。
- 文件是否变化。
- 工具是否可用。
- 权限是否仍然有效。
- 是否存在重复执行风险。

## 5.6 体验六：语音交互

支持：

- 语音输入。
- 实时语音转文字。
- 语音回答。
- 语音触发工具调用。
- 任务执行结果播报。

交互原则：

语音识别和语音合成可以在本地完成；涉及敏感操作时，必须通过屏幕或明确语音确认完成授权，不允许仅凭模糊语音指令执行高风险操作。

# 七、产品边界与非目标

这一部分非常重要。Personal Agent 不应该为了追求“全能”而无限扩大权限。

## 7.1 V1.0 能力边界

| 能力        | V1.0 支持情况 | 边界               |
| --------- | --------- | ---------------- |
| 本地文本对话    | 支持        | 依赖本地模型           |
| 本地文件检索    | 支持        | 用户授权范围内          |
| PDF 内容分析  | 支持        | 受文件解析能力限制        |
| 本地记忆      | 支持        | 用户可管理            |
| Skill 调用  | 支持        | 隔离执行             |
| Python 执行 | 支持        | 独立 Worker        |
| Shell 执行  | 受限支持      | 沙箱和白名单策略         |
| 浏览器自动化    | 基础支持      | 需要浏览器运行环境        |
| 多 Agent   | 基础支持      | 由主 Agent 统一调度    |
| 定时任务      | 基础支持      | 受 Android 后台机制限制 |
| 系统设置修改    | 受限支持      | 仅支持允许的系统 API     |
| 跨应用 UI 操作 | 后续增强      | 受系统权限和应用限制       |
| 云端模型调用    | 非默认能力     | 不纳入离线核心闭环        |

## 7.2 明确不做的事情

V1.0 不承诺：

1. 可以在任何 Android 手机上获得完整系统权限。
2. 可以绕过应用沙箱和 Android 权限体系。
3. 可以不受限制地后台永久运行。
4. 可以在飞行模式下访问互联网。
5. 可以自动操作所有第三方 App。
6. 可以执行任意系统级 Shell 命令。
7. 可以保证所有模型都能在所有手机上运行。
8. 可以保证 Agent 对所有任务都正确理解和执行。
9. 可以在没有授权的情况下读取用户私人数据。
10. 可以自动执行支付、删除等高风险操作。

## 7.3 系统级能力边界

系统级 Agent 与普通 Android 应用存在明显差异。

需要区分三种部署形态：

**形态 A：普通应用**

通过公开 Android API 和用户授权实现能力，适合快速验证 MVP。

**形态 B：预装系统应用**

通过平台签名、特权权限白名单和厂商接口获得扩展能力，适合系统级产品落地。

**形态 C：独立特权服务**

将 Agent Runtime、Tool Broker 和系统能力适配器部署为受系统管理的服务，适合需要严格隔离和长期运行的产品形态。

建议产品目标按照 B + C 设计，保留普通应用模式作为开发和兼容性验证方案。

# 八、非功能需求

## 8.1 性能要求

以下作为 V1.0 初始目标，需通过目标设备矩阵压测确认。

| 指标         | 目标                 |
| ---------- | ------------------ |
| 应用冷启动      | 目标设备 P95 ≤ 3 秒     |
| 首页交互       | P95 ≤ 500ms，不含模型推理 |
| 本地工具调用     | 简单工具 P95 ≤ 1 秒     |
| 本地数据库查询    | 常规查询 P95 ≤ 300ms   |
| Agent 任务恢复 | 状态恢复 P95 ≤ 3 秒     |
| 任务状态刷新     | 关键状态变化后 1 秒内更新     |
| 本地数据访问     | 不依赖外网              |

模型首 Token 延迟、生成速度和内存占用需要根据具体模型与设备分别设定，不应使用单一指标覆盖所有机型。

## 8.2 资源管理

需要重点关注：

- 模型内存占用。
- KV Cache。
- CPU / GPU / NPU 占用。
- 温度。
- 电量。
- 后台任务数量。
- 并发 Worker 数量。

资源管理策略：

1. 默认单个主模型运行。
2. 领域模型按需加载。
3. 非活跃模型自动卸载。
4. 高温时降低推理负载。
5. 低电量时限制后台推理。
6. 限制并发任务数。
7. 大文件采用流式处理。
8. 任务支持断点恢复。

## 8.3 隐私与安全

必须满足：

- 默认离线推理。
- 本地数据加密。
- Keystore 管理密钥。
- 任务级工作区隔离。
- 工具最小权限。
- 文件访问能力句柄化。
- 网络默认关闭。
- 工具调用审计。
- 用户授权可撤销。
- 敏感日志脱敏。

## 8.4 可靠性

- 模型崩溃不应导致整个 Agent 服务崩溃。
- Worker 崩溃不能影响其他 Worker。
- 工具调用必须有超时和取消机制。
- 任务状态必须持久化。
- 应用进程被杀后能够恢复可恢复任务。
- 重复执行必须具备幂等控制。
- 文件写入需要尽可能支持原子提交和备份恢复。

## 9.3 核心架构安全原则

采用决策、授权、执行三权分离。

- Agent 负责决定做什么。
- Policy Engine 负责判断能不能做。
- Tool Broker 负责在授权范围内执行。

Agent 不能直接访问系统底层资源，也不能通过模型输出绕过权限检查。

Android 组件建议：

- Kotlin + Jetpack Compose：原生 UI。
- Binder / AIDL：进程间通信。
- Room / SQLite + FTS5：本地结构化数据和全文检索。
- Android Keystore：密钥管理。
- Foreground Service：用户可感知的长时间任务。
- WorkManager：可延迟、可约束的后台工作。
- llama.cpp / LiteRT-LM 等：本地推理运行时。
- WASM 或独立 UID Worker：不可信 Skill 执行隔离。

重要约束：

系统服务不得直接执行不可信代码。Shell、Python 和第三方 Skill 应进入独立执行 Worker，默认断网，采用任务级工作区和受控文件访问句柄。必要时可以进一步评估 AVF / Linux Guest 隔离环境。

# 十二、最终产品定义

Android Personal Agent 不是一个集成了本地大模型的聊天 App，而是一个面向个人的端侧 Agent Runtime。

它的核心竞争力不在于模型参数规模，而在于：

1. **有记忆：** 理解用户长期上下文。
2. **有工具：** 掌握 Android 系统与应用能力。
3. **会规划：** 能把复杂目标拆解成可执行任务。
4. **能执行：** 可以真正操作本地资源。
5. **可持续：** 支持后台任务和中断恢复。
6. **可治理：** 权限、沙箱、审计和风险控制。
7. **全离线：** 核心能力不依赖云端服务。

最终希望实现的体验是：

用户不再需要思考应该打开哪个 App、使用哪个工具、如何组织操作步骤。

用户只需要表达目标，Personal Agent 理解目标、组织上下文、选择能力、执行任务，并将最终结果交付给用户。

**产品愿景：让每一部 Android 手机，都拥有一个真正属于用户自己的、可执行、可记忆、可持续运行的本地 AI Agent。**

## 十三、建议优先冻结的三个产品决策

这三个决策会直接影响后续 UI、Android 工程架构和研发成本。

| 决策         | 建议方案                    | 原因                 |
| ---------- | ----------------------- | ------------------ |
| 产品部署形态     | 系统预装应用 + 特权服务           | 获得更完整的系统能力         |
| Agent 运行方式 | 主 Agent + 领域 Agent      | 统一调度，避免 Agent 无序协作 |
| 工具安全模型     | Tool Broker + 独立 Worker | 决策、授权、执行三权分离       |

另外，需要特别强调：本地模型推理、Agent Runtime 和工具执行必须解耦。 不能让模型进程承担系统权限，也不能因为模型输出了某条 Shell 命令，就直接交给系统执行。

这与此前确定的 Android 离线 Personal Agent 技术方向保持一致。

## 十四、下一阶段建议：从 PRD 进入产品设计

建议接下来形成三份研发交付物：

1. 高保真 UX 原型：逐页设计首页、对话、任务详情、工具中心、记忆中心、本地模型中心、权限中心。
2. 交互状态说明：覆盖正常、加载、执行、等待授权、失败、离线、后台中断等状态。
3. 研发拆解文档：将功能映射到 Android UI、Agent Runtime、Model Runtime、Tool Broker、Data Service 等模块，形成接口和开发任务。

我建议先做第一项：把当前设计深化成一套完整的、可点击交互的 Android Personal Agent 高保真原型，再以原型反推研发接口和任务拆解。

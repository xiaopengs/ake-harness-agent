# 14 · PRD 需求分析与落地差距

> 对照对象：[`13-prd-android-personal-agent.md`](./13-prd-android-personal-agent.md)（PRD V1.0，2026-11-02）。
> 对照基线：当前 `main`（`e51b9bf`）—— 14 个 Gradle 模块、443 个 Kotlin 文件 / 82,261 行、21 张 Room 表、1177 条测试通过。
> 本文只回答一个问题：**这份 PRD 里，哪些已经能跑、哪些是半成品、哪些在形态 A（普通应用）下根本做不到。**

---

## 0. 结论先行

**PRD 描述的是产品终局，不是下一个迭代。** 把它整份当成 V1.0 排期，会得到一个"每样都做了一点、没有一条闭环"的版本。

三条判断：

1. **能力层已过半，界面层几乎为零。** 任务表、断点、预算、审计、策略、工具注册、记忆卡全在数据库里，但用户能看到的只有「对话 / 助手 / 我的」三个 tab。PRD 的六大功能域里，**任务中心、工具中心、记忆中心三块在 UI 上完全不存在**。
2. **最硬的一条不是功能，是形态。** PRD §7.3 把目标定为 B（预装系统应用）+ C（特权服务），而交付物是 A（普通应用）。B/C 才有的系统签名权限、跨应用 UI 自动化、联系人/日历写入、Shell，在 A 下**不是"做得慢"，是"做不了"**。
3. **V1.0 交付清单 12 条里，真正缺的是一个闭环，不是十二个功能。** 缺的那条闭环是：**授权目录 → PDF 解析 → 分块摘要 → Markdown 落盘 → 可在文件管理器里找到**。这条闭环一旦跑通，PRD §10.1 的标志性 Demo 就成立了；其余 11 条大多是它的支撑件。

### 三份评分（10 分制）

| 维度 | 分数 | 理由 |
|---|---|---|
| 产品完整性 | **9.0** | 能力域、边界、非目标、验收标准齐全，§7.2「明确不做的事」是全文最有价值的一节 |
| 工程可执行性 | **5.0** | 缺状态机迁移表、缺内存/时延预算、把"系统级权限"当默认前提；§4.2.3 的 11 步流水线在 2B 模型上跑不动 |
| 内部一致性 | **6.5** | §7.3 的 B+C 与 §10.1「V1.0 交付」矛盾；§5.2 主动建议与 §8.2 后台限制矛盾；§3.1 五 tab 与"移动优先"的拇指区约束矛盾 |
| 作为需求基线可用度 | **7.5** | 足以冻结"做什么"，不足以直接拆研发任务；需要本文第 5 节的收窄 |

## 1. PRD 要什么 vs 现在有什么

### 1.1 规模对照

| 项 | PRD | 当前实现 |
|---|---|---|
| 一级导航 | 5 个（首页/任务/工具/记忆/我的） | **3 个**（对话 `chats` / 助手 `agents` / 我的 `settings`） |
| 任务状态 | 10 态（Draft/Planning/Waiting Approval/Ready/Running/Paused/Completed/Failed/Cancelled/Interrupted） | **8 态**（CREATED/RUNNING/PAUSED/WAITING_HUMAN/SUCCEEDED/FAILED/IMPOSSIBLE/ABORTED） |
| 内置工具 | 5 大类、40+ 项 | **3 个**（`report_finish` / `export_records` / `remember`）+ MCP 动态工具 + 浏览器 DOM 读取/操作 |
| 记忆检索 | 关键词 + 关联任务 + 知识库 + 向量索引 | **按域名 + 全局**，`ORDER BY pinned, last_used_at`；**无 embedding、无向量、无全文检索** |
| 文档解析 | PDF / Office / OCR / ASR / TTS | **零**（全仓 `pdf` 关键字命中 0 个 Kotlin 文件） |
| 执行隔离 | 独立 Worker（Shell/Python/WASM） | **零**（无 Worker、无沙箱进程） |
| 后台调度 | 定时/周期/条件/事件四类 | 前台服务跑单任务；WorkManager 仅用于数据保留清理（`RetentionJob`）与下载，**未用于用户定时任务** |
| 多 Agent | 主 Agent + 领域 Agent 协同 | **无协同**；`agent_profile` 是"人格"，一次只跑一个 |

### 1.2 关键结构性差异：任务是不是一等公民

这是全文最需要产品拍板的一条，比五 tab 更根本。

- **PRD**：任务是一等对象。用户进"任务中心"，看到正在执行/待确认/已完成/失败/定时；任务详情是时间线，可以暂停、改未执行步骤、重试失败节点。
- **现状**：任务**降级为对话里的一次技能调用**。`ui/nav/AkeNavHost.kt` 的注释写得很直白：

  > "这个 App 原来的形态是'下达一次任务、盯着它跑完'。加了人格之后，用户的主循环变成'找一个角色 → 说句话 → 它自己决定要不要去干活' —— 对话是入口，任务降级成对话里的一次技能调用。"

  后果：`TaskScreen` 存在，但只能从对话里跳进去看某一次执行；**没有"所有任务"的聚合视图**，也没有"待我确认"的队列。

这两套模型不能缝合，只能选一套。选 PRD 那套 = 把 `TaskScreen` 提回底栏 + 新建任务中心（约 5–7 人日）；选现状那套 = PRD §3.2 的整个「02 任务中心」子树作废，§4.2.4 任务详情页降级为对话内的步骤卡。

## 2. V1.0 交付清单 12 条：逐条判定

判定口径：**已有**（能跑且有测试）/ **半成品**（数据层或单侧在，缺另一半）/ **缺失**（零代码）。

| # | PRD §10.1 要求 | 证据（代码位置） | 判定 | 差在哪 |
|---|---|---|---|---|
| 1 | 首页与自然语言对话 | `chat/ChatLoop.kt`、`ui/feature/chat/ChatScreen.kt` | **已有** | 无真机长会话验证；UI 是对话列表，不是 PRD §4.1 的"工作空间" |
| 2 | 本地模型下载、导入、加载 | `llm/ModelLifecycle.kt`、`ModelDownloadService.kt`、`ModelGateScreen.kt` | **已有** | 2.77GB 包、下载耗时未实测；门控页无真机验证 |
| 3 | Agent 任务理解和基础规划 | `agent/planner/StepActionParser.kt`、`AgentLoop.kt` | **半成品** | 是**单步 ReAct 循环**，不是"先出完整计划再执行"；无 Planning/Ready 态 |
| 4 | Tool Registry | `tool_registry` 表（含 `risk_class` / `enabled` / `granted_at`） | **已有** | 缺 UI；用户看不到有哪些工具、不能单独授权 |
| 5 | Tool Broker | `agent/tools/CompositeToolRegistry.kt` + `PolicyEngine` + `HumanGate` | **半成品** | 有"决策-授权-执行"三段，但**执行不隔离**：工具跑在 Agent 进程内 |
| 6 | 文件管理工具 | 无 SAF/文件树工具 | **缺失** | `export_records` 只写自己产出的表格，不读用户文件 |
| 7 | PDF 解析工具 | 无 | **缺失** | 全仓零命中 |
| 8 | 本地记忆 | `memory_card` 表 + `remember` 工具 + `MemoryDao` | **半成品** | 写入有、召回有、**管理 UI 无**；无语义检索，只有域名召回 |
| 9 | 任务执行状态管理 | `TaskEntity` 8 态 + `TaskDao` 状态迁移 | **半成品** | 缺 Planning/Ready 两态 ⇒ 无法表达"计划已出、等用户点开始" |
| 10 | 基础权限确认 | `PolicyDecisionEntity` + `HumanGate` + `agent_capability_grant` | **已有** | 确认文案是工具级，不是 PRD §4.6.4 要求的"操作对象 + 影响范围" |
| 11 | 操作审计 | `trace_event` 表 + `TraceDao` | **已有** | 无导出、无 UI 查询入口 |
| 12 | 任务中断恢复 | `task_checkpoint` + `ChatRehydrator` | **半成品** | 逻辑在；**进程被杀后冷启动恢复未做真机验证** |

**汇总：已有 5 条、半成品 5 条、缺失 2 条。** 缺的两条（文件工具、PDF 解析）恰好是 §10.1 标志性 Demo 的两端 —— 这就是第 0 节说的"缺的是一个闭环"。

## 3. 三处必须先裁决的冲突

### 3.1 五 tab vs 三 tab（会返工，先定）

| | PRD §3.1 | 现状（`docs/12` + `AkeNavHost.TABS`） |
|---|---|---|
| 结构 | 首页 / 任务 / 工具 / 记忆 / 我的 | 对话 / 助手 / 我的 |
| 隐含假设 | 用户会主动管理任务、工具、记忆 | 用户只说话，管理是低频动作 |
| 成本 | 新建 3 个一级页面 + 导航重构 ≈ 5–7 人日 | 0 |

**建议：不恢复五 tab。** 理由三条：

1. 五 tab 在 360dp 宽的屏幕上每项只有 72dp，中文标签（"首页""任务""工具"）在 12sp 下已经贴边；`AkeNavHost` 注释里已经踩过这个坑（"四个 tab 是拇指舒适区的上限"）。
2. "任务/工具/记忆"是**管理型**页面，日活远低于对话；放进"我的"做二级入口，打开成本只多一次点击，但省下三个 tab 位的注意力。
3. `docs/12` 的 UX 方案刚定稿并重构完（29 文件 / +1472 行），此时推翻等于把上一轮全部作废。

**若产品坚持五 tab**：请明确"任务"是聚合视图还是仅"待确认队列"——这两者的数据查询和空态设计完全不同。

### 3.2 云端模型的定位（不是冲突，是措辞要精确）

PRD §7.1 写"云端模型调用｜非默认能力｜不纳入离线核心闭环"。这句和现有实现**不矛盾**：

- 现有默认目标就是 `LOCAL`，云端要用户自己填 BaseURL + Key + 模型名才启用（`CloudBackendCard`）；
- 两条红线仍然成立：DOM 永不进云端、只做 OpenAI 兼容单适配器；
- 回落时通过 `EgressAnnouncementSink` 显式告知用户"已由本机完成"，符合 PRD §5.4"禁止静默切换云模型"。

**唯一要裁决的是入口位置**：现在云端配置在「我的 → 设置」里，PRD 的读者可能期望它更隐蔽（高级选项）。建议保持现状，但在文案上明确"开启后对话内容会离开本机"——现有 `CloudBackendCard` 已有一句，需核对是否够醒目。

### 3.3 形态 A vs B+C（最硬的一条）

PRD §7.3 建议"按 B + C 设计，保留 A 作为验证方案"。但 B/C 需要**平台签名**或**厂商特权白名单**，不是代码能解决的。

形态 A 下**确定做不到**的 PRD 条目：

| PRD 条目 | A 下的真实上限 |
|---|---|
| §4.3.2 联系人操作、日历写入 | 需 `READ_CONTACTS` / `WRITE_CALENDAR` 运行时权限，可申请但商店审核严；**可用，非系统级** |
| §4.3.2 应用启动、通知管理 | 可用（`getLaunchIntentForPackage` / `NotificationListenerService`） |
| §7.1 跨应用 UI 操作 | 仅无障碍服务，**不是** PRD 设想的"系统级自动化"；且各家 ROM 会杀 |
| §4.3.2 Shell | **不可用**（普通应用无 `su`；`Runtime.exec` 只能跑自带二进制，且受 SELinux 限制） |
| §4.3.2 修改系统关键设置 | 仅 `Settings.ACTION_*` 跳转，不能直接改 |
| §4.2.6 精确定时任务 | 受 Doze / 厂商省电策略限制，WorkManager 最小周期 15 分钟 |

**建议：V1.0 明确以 A 交付，并把 PRD 里只有 B/C 才能兑现的条目整体挪到"厂商合作版本"分支。** 否则验收时会出现"功能清单打了勾、真机演示做不出来"的局面。

## 4. PRD 低估的四件事

### 4.1 端侧模型的规划能力（最容易被低估）

PRD §4.2.3 画了 11 步流水线（理解 → 检索 → 规划 → 风险 → 权限 → 调度 → 监控 → 校验 → 交付 → 沉淀）。每一步若都过一次模型，以 2.77GB 的 Gemma 4 E2B 计，**单任务分钟级**，且 2B 模型在 6 步以上计划的成功率会快速衰减。

现有代码已经在为此付代价：`StepActionParser`（容错解析）、`RepairHints`（纠错提示）、`Verifier`（结果校验）、`JsonTolerant`（宽松 JSON）—— 这四个类的存在本身就是"模型不可靠"的工程证据。

**建议**：PRD 的"规划"应改为**模板化计划 + 模型填参**，而不是让模型自由生成 DAG。V1.0 只支持 3–5 步的线性计划。

### 4.2 内存预算

PRD §8.2 只说"关注模型内存占用、KV Cache"。现实是：**模型 2.77GB + 运行时 ≈ 3.3GB 常驻**，实测单次推理 `+551MB RSS` 已接近 OOM 边缘。中低端机（6GB RAM）在与微信/相机共存时基本必崩。

**建议**：PRD 增加一条硬门槛——`minRamGb >= 8` 才允许加载主模型，6GB 设备降级到轻量模型或纯云端。这条现在写在 `model_asset.min_ram_gb` 字段里，但没有产品级表述。

### 4.3 后台存活

PRD §4.2.6 自己承认"不能承诺任意时间都能精确执行"，但 §5.2 的主动建议、§10.2 的定时任务仍按"能跑"设计。国内 ROM（MIUI/EMUI/ColorOS）对后台的限制比 AOSP Doze 更激进，**定时任务在真机上的实际触发率可能低于 60%**。

**建议**：把"定时任务"从 V1.1 的承诺项改成"尽力而为 + 前台服务保底"，并在 UI 上明示"可能延迟"。

### 4.4 WebView ≠ 浏览器自动化

PRD §4.3.2 自己点出了这一点（"不能将普通 WebView 当作完整浏览器自动化环境"），但 §7.1 又写"浏览器自动化｜基础支持"。现状 `browser/WebViewExecutor.kt` 正是 WebView 方案：能取 DOM、能点、能填，但**过不了 Cloudflare、拿不到跨域 iframe、没有多标签**。

**建议**：把"浏览器自动化"在 V1.0 的表述收窄为"**单页 DOM 读取与表单填写**"，不要承诺"网页操作"。

## 5. V1.0 收窄建议

### Must（不做完不能发布）

| 项 | 为什么是 Must | 估时 |
|---|---|---|
| SAF 目录授权 + 文件枚举 | §10.1 Demo 的起点；也是 §4.6.2 文件权限的最小实现 | 3 人日 |
| PDF 文本抽取（本地，无网络） | Demo 的核心；决定"能不能读用户的东西" | 4 人日 |
| 分块 + 摘要 + Markdown 落盘 | Demo 的终点；验证"模型能处理真实文档" | 4 人日 |
| 计划确认（Planning → Ready → Running） | 没有它，高风险操作无法在执行前拦截 | 3 人日 |
| 记忆管理页（列表/删除/来源） | PRD §4.4.3 的硬要求；现在只能写不能管 | 2 人日 |
| 任务列表页（全部任务 + 状态筛选） | 让"任务"可见；否则暂停/恢复无处触发 | 2 人日 |

合计 ≈ **18 人日**（不含真机调试）。这六项做完，PRD §10.1 的 Demo 可以真机演示。

### Should（V1.0 之后第一个迭代）

- 定时任务（WorkManager + 前台服务保底）
- 语音输入（系统 `SpeechRecognizer`，不引入 ASR 模型，省 300MB+）
- 审计日志导出（CSV）
- 工具中心只读页（展示已注册工具 + 风险等级，不做启停）

### Cut（V1.0 明确不做，写进 release note）

| 项 | 砍的理由 |
|---|---|
| 多 Agent 协同 | 单模型的规划可靠性都不够，多 Agent 只是把失败面放大 |
| Skill 市场 / 导入导出 | 无可信来源校验体系前，等于给用户装后门 |
| Shell / Python Worker | 形态 A 下无隔离手段；AVF 需 Android 13+ 且厂商开放 |
| 跨应用 UI 自动化 | 需无障碍 + 厂商白名单，且极易被判定为外挂 |
| 主动建议 | 无数据源、无事件订阅，做出来只能是"猜"；PRD §4.1.2 自己也写了"不允许虚构用户行为" |
| A2A / MCP Gateway | 依赖前四项，属 V2.0 |

## 7. 需要产品拍板的五个问题

1. **任务是一等公民还是对话的附属？**（决定五 tab 与任务中心是否存在，影响 ≈ 7 人日）
2. **V1.0 交付形态是 A 还是等 B？**（决定 Shell/跨应用自动化是否进范围，影响整个 P1）
3. **PDF 解析自研还是引第三方？**（自研 ≈ 4 人日但只支持文本型 PDF；引 PDFBox-Android ≈ +8MB 包体，支持扫描件需再加 OCR ≈ +30MB）
4. **记忆要不要语义检索？**（要 = 引入 embedding 模型（+100–300MB）与向量索引；不要 = 现在这套域名召回就是终态）
5. **"主动建议"在无数据源时是否直接删掉？**（保留会逼着实现方编造用户行为，违反 PRD §4.1.2 自己的红线）

## 8. 验收对齐：把 PRD §11.1 变成可执行断言

PRD 的 12 条验收标准里，有 6 条可以直接写成测试，另外 6 条必须真机验证。分开列，避免"测试全绿 = 产品可用"的错觉。

| PRD 验收项 | 可自动化 | 断言方式 |
|---|---|---|
| 本地模型断网加载推理 | 否 | 真机飞行模式，冷启动到首 token |
| 对话多轮上下文 | 是 | 已有 `ChatLoop` 多轮测试；补一条 20 轮不丢上下文的用例 |
| 工具调用 | 是 | `CompositeToolRegistry` 已有；补"未注册工具必须返回 NOT_FOUND" |
| 未授权工具不能执行 | 是 | `PolicyEngine` 已有拒绝路径测试 |
| 文件只访问授权范围 | 是 | SAF URI 越界访问必须抛 `SecurityException`（需新增） |
| 任务规划展示结构化步骤 | 是 | `StepEntity` 序列化快照比对 |
| 任务跟踪展示真实状态 | 是 | 状态迁移表全覆盖（8 态 × 合法/非法迁移） |
| 进程退出后可恢复 | 否 | 真机 `adb shell am force-stop` 后冷启动 |
| 记忆可查看/编辑/删除 | 是 | `MemoryDao` CRUD 已有；补 UI 层 |
| 工具调用有完整审计 | 是 | `trace_event` 行数与调用次数一致 |
| 不可信代码无法获得系统权限 | 否 | 形态 A 下无 Worker，此项**当前无对象可测** |
| 核心业务无外网依赖 | 否 | 真机断网跑完 M1 闭环 |

**一句话**：现在能自动化的只有 7 条，剩下 5 条全部依赖真机 —— 这也是为什么"1177 条测试通过"不能等同于"产品可用"。
